# 项目讲解与答辩口径

## 30 秒版本

我构建了一个基于 LLM Judge 和 LLM Repair 的生成质量闭环。生成模型给出候选答案后，Judge
会结合原始任务、完整业务上下文和逐项校验标准，输出 pass/fail、分数及结构化问题；失败时
Repair 根据问题清单定向改写，再交给 Judge 复检。运行层限制调用次数、修复轮次和超时，
遇到证据不足、输出协议错误或重复修复时降级。项目用 Qwen3-8B 实现思考判定与修复，并提供
订单回复和 RAG 政策问答场景。

## 为什么必须用 LLM

JSON 类型、枚举和金额范围可由代码严格检查，但“回答是否被政策原文支持”“是否漏掉例外条件”
“修改后是否仍自然且相关”属于开放语义。v0.2 把这些工作交给带完整上下文的 LLM Judge，
避免用硬编码字段映射冒充通用校对能力。

## 为什么还需要程序层

LLM 不能自行可靠地管理无限重试、预算、超时、协议解析和发布边界。程序负责状态机与 fail-closed，
同时保留每轮 verdict 和 Token 数据，便于定位误判与做评测。

## 可以如实表达的内容

| 内容 | 状态 |
|---|---|
| LLM Judge/Repair 数据结构和有界循环 | 已实现并有自动化测试 |
| Qwen3-8B 百炼适配、thinking 参数、环境变量密钥 | 已实现，HTTP 请求有模拟测试 |
| 原始文本 RAG 检索、生成、校对、修复入口 | 已实现 |
| 60 条合成 RAG 评测集 + 独立 claim 级评分 | 已实现，真实运行需使用者密钥 |
| 真实业务准确率或线上收益 | 尚无数据，不能虚构 |
| 绝对防幻觉保证 | 不成立，Judge 也可能误判 |

答辩时最好展示一条 `--repair-demo` 的真实运行记录：初稿、首轮 issues、修复稿、第二轮分数、
调用次数和 Token。比只展示架构图更有说服力。
